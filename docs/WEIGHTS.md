# Weight provenance and DIMER hosting

- Upstream: `microsoft/xclip-base-patch32`
- Immutable revision: `a2e27a78a2b5d802e894b8a1ef14f3a8ce490963` (the Hub's `main` resolved to this commit on 2026-09-14)
- Weight format: SafeTensors (`model.safetensors`, 786,414,772 bytes, float32). The upstream repository also hosts `pytorch_model.bin` (786,535,711 bytes), a pickle checkpoint that DIMER does not accept and this pipeline neither lists nor loads.
- Manifest: `weights/xclip-base-patch32/dimer-base-manifest.json` (9 files: `README.md`, `config.json`, `merges.txt`, `model.safetensors`, `preprocessor_config.json`, `special_tokens_map.json`, `tokenizer.json`, `tokenizer_config.json`, `vocab.json`; 790,034,990 bytes total, per-file SHA-256)
- Upstream weight license: MIT (the checkpoint's `README.md` front matter and the Hub's licence tag; the upstream code repository `microsoft/VideoX` is MIT as well)
- DIMER hosting: MIT permits use, modification, distribution, and commercial use subject to preservation of the copyright notice and permission notice. The Git repository does not vendor the checkpoint (`weights/**/*.safetensors` is git-ignored); DIMER may mirror the pinned snapshot in its model store under the upstream license.
- Fresh clone: `stage_missing_files(allow_download=True)` fetches only the manifest-listed files absent on disk, at the pinned revision, into the snapshot directory; `verify_snapshot()` then checks every file before any load. `weights/**` is marked `-text` in `.gitattributes` so Windows `core.autocrlf` cannot rewrite the committed small files and break their digests.
- Loader trust boundary: Transformers `XCLIPModel` / `XCLIPProcessor` (the `VideoMAEImageProcessor` the snapshot declares — shorter side to 224, centre crop, ImageNet mean/std — plus the CLIP BPE tokenizer) with `trust_remote_code=False`, `local_files_only=True` from the verified directory; nothing is fetched at construction or inference (the smoke run loaded and classified with `HF_HUB_OFFLINE=1`).
- **Pinned-release quirk, worked around:** in `transformers==4.57.6` the `XCLIPProcessor.__call__` `videos=` keyword returns no `pixel_values` (only `images=` does). The package therefore calls the two sub-processors explicitly — `processor.image_processor([frames])` for the clip and `processor.tokenizer(labels)` for the names — and passes `pixel_values` of shape `(1, 8, 3, 224, 224)` to the model; the contract does not depend on which keyword the processor honours.
- Adapter artifacts: `save_artifact` writes the trained tensors (the fusion head — `mit`, `visual_projection`, `prompts_visual_layernorm`, `prompts_visual_projection`, `prompts_generator`; about 41 MB in float32) as `adapter.safetensors` beside a `manifest.json` (`org.valcorza.xclip-base-patch32.adapter.v1`) naming the base model id and revision, the base `model.safetensors` SHA-256, the tensor names, the file size and SHA-256, the closed label set the head was trained on, the training configuration and the epoch history. `from_artifact` re-verifies the base snapshot and checks the manifest, the digest and the exact tensor set before deserialising; an adapter is derived from the clips it was trained on and is not redistributed by this repository.
- Adaptation sample: HMDB51 (Serre Lab, Brown University; Kuehne et al. 2011; **CC BY 4.0**) as repacked into parquet by `mteb/HMDB51`, conversion revision `50bb2abb741074ef0868e59ba51af710c825cd1f`, `default/test/0000.parquet` row group 0 (318 rows, 112,858,960 bytes of AVI + label; every test clip of the first ten action classes, 300 clips kept) read over an HTTPS range request, pinned by SHA-256 and byte total in `samples.py`; cached git-ignored under `weights/hmdb51/`, never vendored. Clips are decoded in memory by PyAV (`av==18.1.0`, BSD-3, bundles FFmpeg) into 8 uniformly spaced frames.
